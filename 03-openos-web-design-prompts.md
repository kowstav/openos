# 3 · Design and ship the OpenOS web experience

Give Muse U1–U3 together. Use U1 while defining the renderer, U2 on the working product routes, and U3 before the final security and release checks. Include the full master plan, especially sections 5, 11–12, 15–19 and 29.

## U1 · Give OpenOS a visual language ordinary people can read

> Act as the product designer, frontend engineer and content designer for the OpenOS responsive web app. Implement the design in the existing Next.js/React/Tailwind routes, React Flow map and trusted app renderer. Start by inspecting the actual routes at phone and desktop widths. Save baseline screenshots, list the first task on each surface, and trace the data behind each prominent claim and action. Preserve deep links and working behaviors. Use the two linked GitHub skills below as optional development references; review and pin the revisions and check license terms before reuse. Improve the repo's audited interface-design skill so deployed Muse can apply these principles through the trusted renderer.
>
> Design direction: a visual catalog of things you can make. Keep the recognizable OpenOS ink-and-citron identity if contrast checks pass. Use quiet neutral surfaces, generous space around previews, one strong action color, readable body type and a restrained display face. Reserve monospace for filenames or code in details. Use a small token system for type, spacing, surfaces, focus, state and motion. Use the widest area for the work itself. On a narrow screen keep the example, task and next action together; on desktop let the user compare or manipulate the artifacts side by side. Avoid decorative gradients, glass panels, repeated eyebrows, fake activity feeds and identical dashboards for every tool.
>
> Build a reusable visual preview system for any repository, including ones never curated. Classify the **input, transformation and output** from the evidence-backed capability schema. Prefer a safe, licensed, locally stored fixture and real output from the pinned operation. If no run exists, use a clearly identified illustrative diagram derived from known types. When evidence is insufficient use a neutral type icon and “Preview unavailable” only where its absence affects the decision. Never pass an illustration off as a result, pull arbitrary README assets into the browser, or send user uploads to a thumbnail/model service. Keep provenance, rights, alt text, dimensions, aspect ratio and preview type in the asset record. Mark decorative duplicate images appropriately.
>
> Concrete art direction:
> - **PDF merge:** two distinguishable miniature invoice page stacks converge into one numbered document. Show page order visually. Detail view opens a real sample merged PDF.
> - **Background removal:** show the same product photo on its original backdrop and on checkerboard transparency. Use a labeled before/after toggle or slider with a keyboard equivalent. Attribute the actual engine. Only show “Made with rembg” for a verified rembg run.
> - **Transcription:** pair a short waveform with an aligned timestamped transcript fragment from a licensed sample. If the runtime is unavailable, show the capability illustration and its availability state; no invented transcript styled as live output.
> - **OCR:** show a receipt crop alongside selectable text from that crop. **Diagram tool:** show a tiny source outline beside rendered nodes. **Data tool:** show untidy rows becoming a clean table or plot. **Unknown repo:** choose input/output primitives from evidence, make the transform legible and link to its support details.
>
> Make a single complete reference slice first: Discover → PDF tool details → select merge and watermark → build → reorder documents → download the result → reopen from My Apps. Then apply the system to photo, audio, OCR, unfamiliar repositories and every product surface. Deliver working components, assets and screenshots, not just a mood board.

## U2 · Implement the screens and edit the copy in place

> Apply this screen and copy specification to the real routes. Use one primary action per decision. Each line of copy must identify the object, explain a consequential choice, or help the user recover. Delete copy that repeats a heading, narrates an obvious control, lists the stack, or promises ownership, savings, privacy or isolation without supporting evidence. Keep license, provenance, provider details, logs and caveats discoverable. Put a consequential limitation next to the action it affects.
>
> **Discover (/).** Put “What would you like to do?” above one prominent search field. Visible label “Find a tool”; placeholder “Try ‘merge PDFs’ or paste a GitHub link”. Examples should run a search that actually works. Use a small set of task categories and a visual results grid. Each card gets an artifact preview, a short outcome title such as “Merge PDFs”, optional one-line distinction, and a status or action that reflects current availability. Put repo name in secondary type. Move stars, stack, long coverage lists and paid prices off the card. Replace the current “Stop renting software” hero and repeated sales copy. Show a retry action for catalog-load failure and “Clear filters” for a filtered empty state.
>
> **Tool details (/repo).** Lead with outcome title, source identity and the largest useful example. For PDF: “Merge and watermark PDFs”, then “Combine invoices in order and add your company name.” Use “Try sample” only for an executable verified sample. Offer “Create app” when an attempt can start and “View requirements” for an unavailable path. Expose “What it can do”, supported inputs/outputs, permissions, processing costs and a comparison of specific paid features where evidence exists. Put commit, license, source links and detailed checks in expandable “Technical details”. Never hide a blocking requirement behind that disclosure.
>
> **Capability selection and builder.** Use selectable action names (“Merge pages”, “Add watermark”). Render the same IDs in a readable input → operation → output map and a keyboard-accessible list; both update the same selection. Show necessary dependencies and where permission is needed. On small screens make the list usable without panning a canvas. Beside the prompt use “How should your app work?” and one relevant example. Show the actual selected steps in order; allow undo/reorder where supported. Send selections in the real request. Explain conflicts inline. During construction show the current server event (“Testing the exported PDF”), cancellation and recoverable errors. Reserve “Open app” for a verified runnable version. Put detailed engineering events under “Build details”. Never animate fictional completion.
>
> **Generated app (/app/[id]) and studios.** Give the app's own task the best space. A PDF workspace gets page thumbnails, reordering with move buttons, watermark controls, preview and “Download PDF”. A photo workspace gets a large before/after canvas, background controls and export. An audio workspace gets a player, timestamped editor and “Export subtitles”. A text tool gets an editor and an appropriate sanitized result view. Build these from versioned declarative components and typed actions. Every meaningful control must change real behavior. Show actual upload constraints at the picker, field validation beside the field, and format/size beside downloads when known. Ask only for permissions used by this action. Do not display “sandbox”, a raw grant ID, or a generic text console on every run.
>
> **My Apps and history (/workspace).** One personal library for saved apps. Use recognisable preview, user-given name, last use and “Open”. Put rename, duplicate, rebuild, versions and delete in an accessible secondary menu. Keep saved plans visually distinct and provide a single empty-state action “Find a tool”. Use history for outcomes, changed steps, failure recovery and rollback. Promote a rebuilt version only after verification. Avoid competing studio shelves that make the same app appear twice.
>
> **Permissions and data.** Ask at the moment of use. Example for a one-time upload: “Use this recording for transcription?” followed by the actual filename, destination and retention period if known. Actions “Allow once” and “Cancel”. Put “Revoke access” in a permission center grouped by app; surface source, expiry and scope there. When permission is denied, show the consequence and the available next action. Remove the policy simulator from the primary consumer workflow; an operator view may retain it with accurate labels. Do not use a padlock in place of consent.
>
> **State vocabulary.** Derive user copy from backend reason codes. Examples: “Ready to use”, “Some tools available”, “Needs a runtime”, “Unsupported here”, “Build failed”, “Blocked for safety”. Distinguish estimates, illustrations, upstream capabilities and tested results. Examples of useful recovery: “This PDF is password-protected. Choose an unlocked copy.” / “Build interrupted. View build details.” Use a specific message only when its cause was observed. At each surface implement loading, empty, partial, offline, failure, denied, retry and success states where applicable. Remove dead controls instead of filling them with placeholder prose.

## U3 · Evaluate the finished experience and fix it

> Test the product from an empty account through search, tool details, capability selection, personalization, build, launch, real work, download and reopen. Run the flow by keyboard and touch. Test at 360/375, 768 and 1440 CSS pixels, zoom/reflow, reduced motion, slow network, unavailable providers and long titles. Inspect actual screenshots at each size, including a generated app with content, a blocked tool and a failed build. Check against WCAG 2.2 AA, with automated checks plus manual focus order, visible focus, accessible names, contrast, target sizes, dialog behavior, status announcements, graph/list equivalence, media controls, dropzone alternatives and drag-free reordering.
>
> Use a five-second comprehension test for the cards: can someone identify the input, outcome and whether they can try it? Use a task test for the product: can someone merge two PDFs, change the order, add a watermark, download the correct pages, and find the app again without knowing the repo name? If participants are available, record anonymized observations. Otherwise perform a clearly labeled heuristic review; never invent usability study results.
>
> Audit the copy line by line. Remove text that competes with the user's task, duplicated disclaimers, repeated example prompts and unsupported “Replaces” or “secure” claims. Keep irreversible consequences visible. Attach before/after screenshots, browser checks and an evidence table mapping each page's primary action to a real backend outcome. Update brittle E2E selectors to use accessible roles and observable results; keep coverage when removing obsolete wording. Check image budgets, layout shifts, slow initial load and oversized JS for graph/media-heavy routes. Fix defects, rerun tests and report the remaining limitations.
